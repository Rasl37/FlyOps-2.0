Экспериментальная биоморфная распределенная архитектура, реализующая симуляцию среза нервной системы дрозофилы (*Drosophila melanogaster*) из 19 взаимосвязанных нейронов внутри кластера Kubernetes.

Проект демонстрирует концепции высокой доступности (High Availability) распределенных систем, устойчивости микросервисного меша, динамического обнаружения сервисов (Service Discovery через CoreDNS), предотвращения штормов запросов (Storm Prevention), двухуровневого самовосстановления (L4 self-healing ReplicaSet + L7 перемаршрутизация при сбое сокетов) и сквозной визуализации топологии в реальном времени через Prometheus Operator и Grafana Node Graph.

## Архитектурный обзор

FlyOps 2.0 проецирует биологические нейронные цепи на децентрализованный микросервисный граф, где каждый нейрон представляет собой автономную сетевую единицу в изолированном контейнере. В архитектуре отсутствует единая точка отказа (SPOF) и центральный брокер сообщений: передача потенциала действия выполняется через асинхронные P2P HTTP/TCP вызовы с динамическим разрешением через DNS-фабрику Kubernetes.

### Микросервисная изоляция и маппинг подов
Каждый нейрон коннектома функционирует как независимый контейнеризованный процесс, изолированный от соседних компонентов. Kubernetes гранулярно управляет ресурсами каждого пода, обеспечивая независимые квоты CPU/RAM, жизненный цикл через liveness/readiness пробы и прямое DNS-разрешение.

### Ключевые инженерные решения

1. **Децентрализованный Service Discovery**: Узлы взаимодействуют напрямую по внутренним FQDN именам CoreDNS (`http://neuron-XX.flyops.svc.cluster.local:8080/stimulate`). Центральный оркестратор маршрутизации в рантайме отсутствует.
2. **Защита от штормов через рефрактерный период (400 мс)**: В биологии нейрон физически не способен повторно возбуждаться во время фазы деполяризации. В FlyOps реализован жесткий рефрактерный барьер 400 мс на каждом поде. Все импульсы, приходящие в течение этого интервала, отбрасываются с HTTP-кодом `429 Too Many Requests / Dropped`. Это предотвращает циклический саморазогрев сети и паралич процессора (CPU Starvation).
3. **Двухуровневый Self-Healing**:
   - **Уровень 4 (Инфраструктурный / Оркестратор)**: Контроллер Kubernetes `ReplicaSet` непрерывно сверяет состояние кластера. При падении контейнера из-за нехватки памяти (OOMKilled) или системного сбоя под немедленно пересоздается, возвращаясь в строй за считанные секунды.
   - **Уровень 7 (Прикладной / Сервисный меш)**: Если исходящее TCP-соединение не получает ответа дольше 50 мс или возвращает ошибку 5xx, микросервис-отправитель активирует динамический fallback-роутинг, мгновенно перенаправляя импульс по резервной синаптической ветви без потери целостности сквозного сигнала.
4. **Сквозная наблюдаемость (Observability)**: Сбор кастомных OpenMetrics через Prometheus Operator и формирование направленного взвешенного графа в панели Grafana Node Graph с отображением задержек на ребрах и частоты срабатываний.

## Механизмы отказоустойчивости

### 1. Подавление широковещательного шторма (Anti-Cascade)
В сложных нейронных сетях с рекуррентными петлями положительная обратная связь неизбежно провоцирует лавинообразное распространение трафика (broadcast storm).

FlyOps 2.0 предотвращает каскадный коллапс с помощью атомарной проверки временной метки внутри асинхронного цикла обработки:

$$\Delta t = t_{\text{current}} - t_{\text{last\_depolarization}}$$

$$\text{Действие} = \begin{cases} \text{Провести импульс дальше}, & \text{если } \Delta t \ge 400\text{ мс} \\ \text{Инкремент счетчика отброшенных и Abort}, & \text{если } \Delta t < 400\text{ мс} \end{cases}$$

Эта математическая граница гарантирует детерминированное потребление системных ресурсов даже при жесткой аномальной внешней нагрузке на входной сенсорный слой.

### 2. Динамический L7-фейловер синапсов
Каждый микросервис хранит собственную таблицу смежности синаптических путей. Если основной downstream-узел не отвечает в пределах установленного окна задержки, клиент активирует резервное плечо:

```python
async def forward_pulse(primary_target: str, fallback_target: str, payload: dict):
    try:
        async with aiohttp.ClientSession() as session:
            async with session.post(primary_target, json=payload, timeout=0.050) as resp:
                if resp.status == 200:
                    METRICS_FORWARDED.labels(status="success", route="primary").inc()
                    return await resp.json()
    except (asyncio.TimeoutError, aiohttp.ClientError):
        METRICS_FAILOVER.inc()
        # Переключение на резервный синаптический маршрут
        async with aiohttp.ClientSession() as session:
            async with session.post(fallback_target, json=payload, timeout=0.050) as resp:
                METRICS_FORWARDED.labels(status="success", route="fallback").inc()
                return await resp.json()
```

### 3. Автоматическое восстановление уровня L4 (Kubernetes)
Каждый под обеспечен конфигурацией `livenessProbe` и `readinessProbe` по эндпоинту `/healthz`. При утечке памяти, блокировке цикла событий (deadlock) или фатальном сбое рантайма kubelet принудительно убивает дефектный контейнер и запускает чистый инстанс.

## Инструкция по развертыванию

### Требования к окружению
- ОС: Linux (рекомендуется Ubuntu 22.04 LTS или Debian 12)
- [Minikube](https://minikube.sigs.k8s.io/docs/start/) (версии 1.30.0+) или готовый кластер Kubernetes v1.28+
- Установленный и настроенный CLI `kubectl`
- Менеджер пакетов `helm` v3+

### Шаг 1: Инициализация кластера Minikube
Запустите локальный кластер, выделив ресурсы под работу 19 микросервисов и стека мониторинга:

```bash
minikube start \
  --cpus=4 \
  --memory=8192 \
  --disk-size=25g \
  --driver=docker \
  --kubernetes-version=v1.28.3
```

Проверьте готовность ноды:
```bash
kubectl get nodes
```

### Шаг 2: Установка Prometheus Operator
Разверните стек мониторинга Prometheus Operator для поддержки кастомного ресурса `ServiceMonitor` и веб-интерфейса Grafana:

```bash
helm repo add prometheus-community [https://prometheus-community.github.io/helm-charts](https://prometheus-community.github.io/helm-charts)
helm repo update

helm install monitoring-stack prometheus-community/kube-prometheus-stack \
  --namespace monitoring \
  --create-namespace \
  --set prometheus.prometheusSpec.serviceMonitorSelectorNilUsesHelmValues=false
```

### Шаг 3: Деплой манифестов FlyOps
Примените конфигурации, сервисы обнаружения и все три слоя нейросети:

```bash
# 1. Создание изолированного пространства имен
kubectl apply -f k8s/00-namespace.yaml

# 2. Применение топологической матрицы
kubectl apply -f k8s/01-configmap-topology.yaml

# 3. Деплой микросервисов трех нейронных слоев
kubectl apply -f k8s/02-neurons-sensory.yaml
kubectl apply -f k8s/03-neurons-inter.yaml
kubectl apply -f k8s/04-neurons-motor.yaml

# 4. Применение ServiceMonitor для сбора метрик
kubectl apply -f k8s/05-servicemonitor.yaml
```

Убедитесь, что все 19 подов перешли в статус `Running`:
```bash
kubectl get pods -n flyops -w
```

## Chaos Engineering и тестирование отказоустойчивости

### Сценарий А: Тест L7-фейловера при гибели узла
Смоделируйте аварийное падение промежуточного нейрона реле прямо во время передачи активного импульса:

```bash
# Принудительное удаление пода работающего нейрона обработки
kubectl delete pod -n flyops -l app=neuron-8152 --now
```

**Реакция системы в рантайме**:
Когда целевой узел падает, вышестоящий нейрон-отправитель фиксирует недоступность сокета (`[Errno 111] Connection refused`). Вместо обрыва цепочки вызывающий узел мгновенно активирует резервный синаптический маршрут в обход сбоя.

### Сценарий Б: Тест L4-самовосстановления критического узкого горлышка
Смоделируйте краш ключевого узла-бутылочного горлышка для проверки скорости реакции оркестратора:

```bash
# Принудительный сбой узкого горлышка и замер времени поднятия
kubectl delete pod -n flyops -l app=neuron-4490 --now && \
kubectl get pods -n flyops -l app=neuron-4490
```

**Реакция системы в рантайме**:
Контроллер Kubernetes `ReplicaSet` мгновенно регистрирует отклонение от желаемого состояния. В течение 3 секунд создается и переходит в статус `Running` новый под, восстанавливая баланс в кластере.

### Сценарий В: Тест защиты от шторма запросов (Anti-Cascade Rate Limiter)
Подайте на сенсорный вход высокочастотный стресс-поток (100+ req/sec):

```bash
hey -n 500 -c 10 -m POST \
  -H "Content-Type: application/json" \
  -d '{"stimulus": "hyper_burst", "amplitude": 1.0}' \
  http://$(minikube ip):$(kubectl get svc neuron-01 -n flyops -o jsonpath='{.spec.ports[0].nodePort}')/stimulate
```

**Реакция системы в рантайме**:
- Микросервисы пропускают ровно 1 импульс за интервал в 400 мс.
- Паразитный трафик отсекается с HTTP-статусом 429 без утилизации ядер процессора.
- Потребление оперативной памяти остается неизменным, риск каскадного отказа нод по OOMKilled полностью исключен.

## Справочник метрик Prometheus

Каждый под микросервиса экспортирует по пути `/metrics` следующие метрики:

| Имя метрики | Тип | Описание |
| :--- | :--- | :--- |
| `flyops_spikes_received_total` | Counter | Общее количество импульсов, поступивших на данный узел |
| `flyops_spikes_forwarded_total` | Counter | Количество импульсов, успешно переданных дальше (с лейблом целевого узла) |
| `flyops_refractory_drops_total` | Counter | Количество импульсов, заблокированных рефрактерным периодом 400 мс |
| `flyops_l7_failover_events_total` | Counter | Число переключений на резервный маршрут из-за сбоя downstream-сокета |
| `flyops_propagation_latency_seconds` | Histogram | Время прохождения сигнала по синаптическому звену |
